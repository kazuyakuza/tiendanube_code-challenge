# TODO 01 – Project Foundation

## Goal

Bootstrap the NestJS application and establish the non-business infrastructure that every subsequent feature will rely on:

- NestJS project skeleton and dependencies
- Validated configuration via `.env`
- Global HTTP middleware and security hardening
- URI versioning and Swagger skeleton
- Public health endpoint
- API Key authentication guard

This TODO deliberately contains **no business logic** related to transactions, receivables or the Numerator service.

## Context

The repository already contains some files.
The NestJS application should be created **alongside** those files (inside `src/`). Do not overwrite or move the existing assets.

## 2. Configuration Module (validated `.env`) [DONE]

### 2.1 Environment variables

Create a `.env.example` (and a real `.env` for local development) containing at least:

```env
NODE_ENV=development
PORT=3001

# External services (provided by docker-compose)
NUMERATOR_API_URL=http://localhost:3000
JSON_SERVER_URL=http://localhost:8080

# Security
API_KEY=your-secret-api-key-here
```

### 2.2 Validation class

Create a dedicated configuration class `src/config/env.validation.ts` that:

- Uses `class-validator` decorators (`@IsString()`, `@IsNotEmpty()`, `@IsEnum()`, `@IsUrl()`, `@IsInt()`, `@Min()`, etc.)
- Is validated at application bootstrap via `ConfigModule.forRoot({ validate: ... })`
- Throws a clear error and prevents the application from starting if any required variable is missing or invalid

Recommended validated fields:

| Variable            | Type / Rules                          |
|---------------------|---------------------------------------|
| `NODE_ENV`          | enum: `development` \| `production` \| `test` |
| `PORT`              | integer, > 0                          |
| `NUMERATOR_API_URL` | valid URL, required                   |
| `JSON_SERVER_URL`   | valid URL, required                   |
| `API_KEY`           | non-empty string                      |

### 2.3 ConfigModule registration

Register `ConfigModule.forRoot` as a global module in `AppModule` so that `ConfigService` can be injected anywhere without re-importing.

## 3. Application Bootstrap (`main.ts`)

In `main.ts` configure the following cross-cutting concerns **before** the application starts listening:

### 3.1 Security

- Enable `helmet()` with sensible defaults.
- Enable CORS. For local development it is acceptable to allow all origins; the configuration should be easy to tighten later (ideally driven by an env variable).

### 3.2 Logging

- Integrate `morgan` in “dev” or “combined” format so that every incoming HTTP request is logged to stdout.
- Morgan should run as Express middleware (NestJS allows this via `app.use(morgan(...))`).

### 3.3 Global Validation Pipe

Register a global `ValidationPipe` with at least:

- `whitelist: true` – strip properties that do not have decorators
- `forbidNonWhitelisted: true` – reject requests that contain unknown properties
- `transform: true` – automatically transform payloads to DTO instances

### 3.4 URI Versioning

Enable URI versioning so that business endpoints live under `/v1/...`:

```ts
app.enableVersioning({
  type: VersioningType.URI,
  defaultVersion: '1',
});
```

Health endpoints may remain unversioned.

### 3.5 Swagger

Set up a basic Swagger document:

- Title, description and version of the API
- Bearer/API-Key security scheme (header name: `x-api-key`)
- Mount the UI under `/docs` (or `/api`)
- Include a env var to enable/disable it.

At this stage Swagger can be almost empty; later TODOs will enrich it with DTOs and operations.

### 3.6 Port

Listen on the port provided by the validated configuration (`ConfigService.get('PORT')`).

## 4. Health Module

### 4.1 Endpoint

Implement a single endpoint:

```http
HEAD /health/ping
```

- Must return **200 OK** with an empty body.
- Must be **public** (no API Key required).
- Should not be versioned (or can live outside the `/v1` prefix).

### 4.2 Implementation notes

- Create a dedicated `HealthModule` + `HealthController`.
- The handler can be extremely simple (just return, or return `{ status: 'ok' }` if a body is preferred for GET, but the required method is `HEAD`) or handle it with just decorators.
- NestJS supports `@Head()` decorator.
- Include a JSDoc in the method on how to call it using curl.

## 5. API Key Guard

### 5.1 Behaviour

- Requests to protected routes must include the header `x-api-key`.
- The value must match exactly the `API_KEY` defined in the environment.
- If the header is missing or incorrect → respond with **401 Unauthorized**.
- The health endpoint must remain accessible without the header.

### 5.2 Implementation approach

Recommended pattern:

1. Create an `ApiKeyGuard` that implements `CanActivate`.
2. Inject `ConfigService` to read the expected key.
3. Apply the guard in one of these ways (choose the cleanest):
   - Globally, then exclude the health route with a custom decorator / metadata, **or**
   - Only on the modules/controllers that need protection (later the Transactions module).

At this stage it is enough that the guard exists and can be applied. The Transactions controller will be created in a future TODO; for now you can leave a placeholder protected route or simply register the guard so it is ready.

### 5.3 Swagger integration

Document the `x-api-key` header as a security scheme so that the “Authorize” button in Swagger UI works.

## 7. Out of scope for this TODO

- Any transaction / receivable logic
- Communication with Numerator API or json-server
- DTOs related to payments
- Unit or e2e tests (will come later)
- Advanced error filters or interceptors (can be added when needed)

## 8. Implementation guidance

- Prefer NestJS idiomatic patterns (modules, providers, dependency injection).
- Keep the code readable and explicit; this is a challenge that will be reviewed.
- Do not hard-code URLs or secrets; everything must come from the validated configuration.
- After finishing, the application should start cleanly with `npm run start:dev`, expose the health endpoint, reject requests without a valid API key on protected routes, and show a working (although almost empty) Swagger UI.
