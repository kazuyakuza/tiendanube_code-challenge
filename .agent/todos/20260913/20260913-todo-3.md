# TODO 02 – Transaction DTOs & Request Validation

## Goal

Define the complete set of Data Transfer Objects (DTOs) that represent the contract of `POST /v1/transactions`.

By the end of this TODO the application must be able to:

- Accept a well-formed JSON payload for creating a transaction
- Reject invalid payloads with clear validation errors (400)
- Expose the request and response shapes in Swagger
- Keep sensitive card data under control (only last 4 digits are ever stored/returned)

No business logic, no calls to external services, and no persistence yet.  
This TODO is purely about the **shape and validation** of the data that enters and leaves the API.

## Context

The foundation from TODO 01 is already in place (NestJS app, ConfigModule, ValidationPipe, Swagger skeleton, API Key guard, health endpoint).

The global `ValidationPipe` was configured with:

- `whitelist: true`
- `forbidNonWhitelisted: true`
- `transform: true`

Therefore every incoming property that is not decorated will be stripped or rejected.  
All DTOs must be fully decorated with `class-validator` and `@ApiProperty` / `@ApiPropertyOptional`.

## Task 1. Request DTO – Create Transaction

### 1.1 Endpoint contract

```http
POST /v1/transactions
Header: x-api-key: <API_KEY>
Content-Type: application/json
```

### 1.2 Expected request body (from the challenge)

The client sends the raw transaction data.  
The API is responsible for generating the `id` and for creating the corresponding receivable.

Fields the client **must** provide:

| Field                 | Type   | Rules / Notes                                      |
|-----------------------|--------|----------------------------------------------------|
| `value`               | string | Decimal amount as string (e.g. `"250.00"`, `"100"`). Must be a valid positive number. |
| `description`         | string | Non-empty. Example: `"T-Shirt Black M"`            |
| `method`              | string | Exactly one of: `debit_card` \| `credit_card`      |
| `cardNumber`          | string | Full card number as received from the client. The service will later keep **only the last 4 digits**. |
| `cardHolderName`      | string | Non-empty                                          |
| `cardExpirationDate`  | string | Format `MM/YY` (e.g. `"04/28"`)                    |
| `cardCvv`             | string | Typically 3 or 4 digits. Keep it as string.        |

> Important: the client does **not** send `id`. The ID is generated by the orchestration layer (future TODO) using the Numerator API.

### 1.3 Validation requirements

Create a DTO class (suggested name: `CreateTransactionDto`) that enforces:

- All fields listed above are **required**.
- `method` is restricted to the two allowed values (use an enum).
- `value` must represent a positive decimal number. Convert to valid number and validate.
- `cardExpirationDate` keep as string, but validate it is a valid future date.
- `cardCvv` should be a short numeric string (3–4 characters is a reasonable constraint). Keep it as string and validate it is a non empty number string.
- `cardNumber` should be a numeric string of reasonable length (the exact PCI rules are out of scope; a basic length + digits check is enough).
- Unknown properties must be rejected (already handled by the global pipe).

### 1.4 Swagger annotations

Every property must have an `@ApiProperty` (or `@ApiPropertyOptional`) with:

- `description`
- `example`
- `enum` when applicable (`method`)

This way the Swagger UI becomes a usable playground as soon as the controller is wired (future TODO).

## Task 2. Response DTOs

The successful response of `POST /v1/transactions` should return **both** resources that were created, so the caller has a complete picture.

Suggested top-level response shape:

```json
{
  "transaction": { ... },
  "receivable":  { ... }
}
```

### 2.1 Transaction response shape

Matches what json-server stores and what the challenge expects:

| Field                 | Type   | Notes                                              |
|-----------------------|--------|----------------------------------------------------|
| `id`                  | string | Generated via Numerator                            |
| `value`               | string | Same as request                                    |
| `description`         | string | Same as request                                    |
| `method`              | string | `debit_card` or `credit_card`                      |
| `cardNumber`          | string | **Only last 4 digits**                             |
| `cardHolderName`      | string |                                                    |
| `cardExpirationDate`  | string | `MM/YY`                                            |
| `cardCvv`             | string | As received (or masked if you prefer; the challenge sample keeps it) |

### 2.2 Receivable response shape

| Field            | Type   | Notes                                                                 |
|------------------|--------|-----------------------------------------------------------------------|
| `id`             | string | Generated via Numerator                                               |
| `transaction_id` | string | References the transaction `id`                                       |
| `status`         | string | `paid` (debit) or `waiting_funds` (credit)                            |
| `create_date`    | string | ISO-8601 or the format used by the seed data                          |
| `subtotal`       | string | Same as transaction `value`                                           |
| `discount`       | string | Fee **percentage** as string: `"2"` or `"4"` (see brief clarification)|
| `total`          | string | `subtotal × (1 - discount/100)` formatted as string                   |

### 2.3 Implementation notes for response DTOs

- Create dedicated classes (`TransactionResponseDto`, `ReceivableResponseDto`, `CreateTransactionResponseDto`).
- These classes are mainly for Swagger documentation and for type safety inside the service layer.
- They do **not** need heavy `class-validator` decorators (they are output, not input), but they **must** have complete `@ApiProperty` annotations.
- Reuse enum for `PaymentMethod` and for `ReceivableStatus`.

### 2.4 Config to Disabled default behaviour

Add a .env config so disable this default behaviour, when disabled just returns 201 CREATED.

## Task 3. Supporting Enums / Constants

Define (and export) the following so they can be reused by DTOs, services and tests later:

```ts
enum PaymentMethod {
  DEBIT_CARD = 'debit_card',
  CREDIT_CARD = 'credit_card',
}

enum ReceivableStatus {
  PAID = 'paid',
  WAITING_FUNDS = 'waiting_funds',
}
```

Fee percentages (for documentation and later business logic):

| Method         | Fee % | Stored in `discount` |
|----------------|-------|----------------------|
| `debit_card`   | 2     | `"2"`                |
| `credit_card`  | 4     | `"4"`                |

Maybe in a app constants file.

## Task 4. Card number handling (design decision)

- The **request DTO** accepts the full card number (so the client can send it).
- The **response DTO** (and later the payload sent to json-server) must contain **only the last 4 characters**.
- The truncation/masking logic itself belongs to the service layer (future TODO).  
  In this TODO you only need to document the expected shape and, if you want, provide a small pure helper function such as `maskCardNumber(full: string): string` that can be unit-tested later.
