# TODO 04 – Transaction Orchestration Logic

## Goal

Implement the core business logic that turns a validated `CreateTransactionDto` into a persisted transaction + receivable pair.

This is the heart of the API:

1. Obtain two unique IDs from the Numerator service (before any write).
2. Mask the card number.
3. Calculate the fee and build the receivable data according to the payment method rules.
4. Persist both resources through the json-server client.
5. Return a consistent response containing both created resources.

No HTTP controller is required yet (that belongs to the next TODO).  
Focus exclusively on a clean, testable service method.

## Context

- TODO 02 provided the request/response DTOs and the enums (`PaymentMethod`, `ReceivableStatus`).
- TODO 03 provided `NumeratorService.getNextId()` and `JsonServerService.createTransaction` / `createReceivable`.
- The global ValidationPipe already guarantees that the service receives a valid DTO.

## Task 1. Service responsibility [DONE]

Create a `TransactionsService` (inside a `TransactionsModule`) with a single public method like:

```ts
async create(dto: CreateTransactionDto): Promise<CreateTransactionResponseDto>
```

## Task 2. Required flow (strict order) [DONE]

```text
1. Obtain transactionId  = await numeratorService.getNextId()
2. Obtain receivableId   = await numeratorService.getNextId()
3. Mask card number       → keep only the last 4 digits
4. Calculate fee data     → status, discount, total, create_date (and payment date rules)
5. Build transaction payload (with masked card + transactionId)
6. Build receivable payload (with receivableId + transactionId + fee data)
7. Persist transaction    → jsonServerService.createTransaction(...)
8. Persist receivable     → jsonServerService.createReceivable(...)
9. Return { transaction, receivable } → this is the default behaviour. Defined .env config can disabled this and just returns 201 CREATED
```

## Task 3. Fee calculation rules [DONE]

| Payment Method | Fee % | `discount` value | Receivable `status` | Date rule                          |
|----------------|-------|------------------|---------------------|------------------------------------|
| `debit_card`   | 2     | `"2"`            | `paid`              | same day (D+0)                     |
| `credit_card`  | 4     | `"4"`            | `waiting_funds`     | creation date + 30 days (D+30)     |

### Concrete calculations

- `subtotal` = transaction `value` (string)
- `discount` = `"2"` or `"4"` (string – percentage, matching the seed data)
- `total`    = `subtotal × (1 - discount/100)`  
  Format the result as a string. Use 2 decimals places, just drop the remaining decimals if more than 2.

### Date handling

- `create_date` should be "now" in string format `DD/MM/YYYY`.
- For `credit-card` receivables the business rule mentions a payment date of D+30 ("now" + 30 days), also in string format `DD/MM/YYYY`.

## Task 4. Card number masking [DONE]

Implement a small pure helper in a shared util:

```ts
maskCardNumber(fullCardNumber: string): string
// returns only the last 4 characters
```

Use it when building the transaction payload that will be sent to json-server and returned to the client.

## Task 5. Error behaviour [DONE]

At this stage keep the error handling straightforward:

- If `getNextId()` throws → let the error propagate (the future controller / exception filter will turn it into an HTTP response).
- If `createTransaction` succeeds but `createReceivable` fails → the system is left in a partially written state.  
  For this TODO it is acceptable to let the error propagate.  
  A more sophisticated compensation / cleanup strategy will be addressed in the next TODO together with the controller and global error handling.

Do **not** swallow errors. The caller must be able to distinguish success from failure.

## Module wiring

- `TransactionsModule` should import `NumeratorModule` and `JsonServerModule`.
- Export `TransactionsService` so the future controller can inject it.
- No controller is required in this TODO.


## Out of scope for this TODO

- HTTP controller and route registration
- API Key guard application on the endpoint
- Swagger operation decorators
- Advanced compensation / saga logic if the second write fails
- Unit or e2e tests

## Implementation guidance

- Keep the public `create` method readable; extract private helpers for fee calculation, date formatting and payload mapping if they improve clarity.
- Prefer pure functions for money math and masking so they are easy to unit-test later.
- Monetary values stay as strings in the public API and in the payloads sent to json-server (consistent with the challenge).
