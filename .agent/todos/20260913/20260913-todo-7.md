# TODO 06 – Unit & E2E Tests

## Goal

Add a focused test suite that proves the critical behaviour of the Orchestration API:

1. **Unit tests** – pure logic and service-level behaviour in isolation (fee calculation, card masking, ID generation retries, orchestration flow with mocked dependencies).
2. **E2E tests** – full HTTP flow against a running NestJS application (health check, authentication, validation, successful creation, error cases).
3. **Concurrency tests** – parallel requests competing for IDs and partial-failure scenarios under concurrent load.

## Context

- The application is fully implemented (TODOs 01–05).
- External services (Numerator API and json-server) are started via `docker compose` by the user when needed. Tests must not run docker commands themselves.
- Prefer the testing tools already present in a standard NestJS project: **Jest** (unit) and **Supertest** (e2e).

## Task 1. Unit tests

### 1.1 What to test (priority order)

| Area                         | What to assert                                                                 | How |
|-----------------------------|---------------------------------------------------------------------------------|-----|
| Card masking helper         | Returns only the last 4 digits; handles short / normal inputs                   | Pure function test |
| Fee calculation             | Correct `discount`, `status`, `total` for `debit_card` and `credit_card`        | Pure function or private-method test via service |
| Date formatting             | `create_date` (and payment date if implemented) use `DD/MM/YYYY`                | Pure function test |
| `NumeratorService.getNextId`| Success on first CAS; retries on conflict; throws after max retries             | Mock `HttpService` |
| `TransactionsService.create`| Happy path (two IDs → mask → fee → both writes → response shape)               | Mock Numerator + JsonServer services |
| Partial failure             | When receivable creation fails, compensation (`DELETE` transaction) is attempted | Mock JsonServer to fail on receivable / succeed on delete |

### 1.2 Guidelines

- Mock all HTTP calls. Unit tests must **not** depend on the real Numerator API or json-server.
- Prefer testing pure helpers directly when they exist (masking, fee math, date formatting).
- For service tests, inject mocked dependencies through the NestJS testing module (`Test.createTestingModule`).
- Keep tests readable and documented: arrange → act → assert.
- Avoid testing NestJS framework internals or trivial getters.

## Task 2. E2E tests

### 2.1 Setup

- Use the standard NestJS e2e setup `test/app.e2e-spec.ts`.
- Bootstrap the real application module.
- External services (Numerator + json-server) are expected to be running. If they are not available, the e2e suite may fail fast with a clear message; do not try to start Docker from the tests.
- Read `API_KEY` (and any other needed values) from the same configuration mechanism the app uses, or from a test-specific `.env`.

### 2.2 Cases to cover

| # | Case                                      | Expected result                                      |
|---|-------------------------------------------|------------------------------------------------------|
| 1 | `HEAD /health/ping`                       | `200` with empty body                                |
| 2 | `POST /v1/transactions` without API key   | `401`                                                |
| 3 | `POST /v1/transactions` with invalid key  | `401`                                                |
| 4 | `POST /v1/transactions` with invalid body | `400` (validation errors)                            |
| 5 | `POST /v1/transactions` happy path (debit)| `201` + correct transaction & receivable (or empty body if config disabled) |
| 6 | `POST /v1/transactions` happy path (credit)| same as above, with `waiting_funds` and 4% fee     |

For the happy-path cases also assert:

- Card number in the response (if body is returned) contains only 4 digits.
- `discount` / `status` / `total` match the fee rules.
- Both resources actually exist afterwards (optional extra `GET` to json-server if you want stronger guarantees).

### 2.3 Guidelines

- Do not leave residual data assumptions that make tests order-dependent when avoidable.  
  (Because json-server and the Numerator are shared mutable state, perfect isolation is hard; keep assertions focused on the response of the call under test.)
- Clean up created resources by directly modifying the `db.json` file.

## Task 3. Concurrency cases

These tests exercise the most important part: unique ID generation under concurrent load and the behaviour when something fails in the middle of the orchestration.

Implemented as **e2e tests** against the real Numerator + json-server.

### 3.1 Scenarios to cover

| # | Scenario | What to simulate | Expected outcome |
| --- | ---------- | ------------------ | ------------------ |
| 1 | **Parallel success** | N concurrent `create()` calls (e.g. 5–10), all dependencies succeed | All requests return `201`. Every generated ID is unique. No duplicate transaction or receivable IDs. |
| 2 | **CAS conflict then success** | First `test-and-set` fails (numerator already moved), second attempt succeeds | `getNextId()` retries and eventually returns a valid unique ID. Caller still succeeds. |
| 3 | **CAS exhausted** | Every `test-and-set` returns conflict up to `MAX_RETRIES` | `getNextId()` throws the domain error (retries exhausted). No write to json-server occurs. |
| 4 | **Failure on first ID** | `getNextId()` fails on the very first call (Numerator down / timeout) | Orchestration aborts before any write. No transaction and no receivable are created. |
| 5 | **Failure on second ID** | First `getNextId()` succeeds, second `getNextId()` fails after retries | Orchestration aborts before any write. No transaction and no receivable are created. |
| 6 | **Failure on createTransaction** | Both IDs obtained, but `createTransaction` fails | No receivable is created. Error propagated to caller. |
| 7 | **Failure on createReceivable + compensation success** | Transaction persists, receivable fails, `DELETE /transactions/:id` succeeds | Compensation runs. Final state has neither resource (or only the cleaned-up transaction is gone). Client receives an error. |
| 8 | **Failure on createReceivable + compensation failure** | Transaction persists, receivable fails, compensation `DELETE` also fails (even after its own retries) | Inconsistency is logged. Client still receives an error. Orphan transaction may remain (document this limitation). |

### 3.2 Implementation notes

- Fire several `POST /v1/transactions` in parallel with `Promise.all` (Supertest or raw axios).
- Assert all responses are `201` and that the set of returned IDs has no duplicates.
- Requires Numerator + json-server running; clean `db.json` afterwards.

### 3.3 What “correct” means under concurrency

- No two successful requests share the same transaction ID or the same receivable ID.
- A request that fails while obtaining IDs never leaves data behind.
- A request that fails after the transaction write triggers compensation (as defined in TODO 05).
- The API never returns `201` for a partially completed orchestration.

## Out of scope

- Load / performance tests
- Contract tests against a mocked OpenAPI server
- Mutation testing or snapshot testing of entire responses
- CI pipeline configuration

## Implementation guidance

- Start with the pure helpers (masking + fee calculation); they give quick feedback and high confidence.
- Then add `NumeratorService` retry tests with a mocked `HttpService`.
- Then the orchestration service tests with both clients mocked (including the concurrency / partial-failure matrix above).
- Finish with the e2e happy path, auth/validation negatives, and optionally one parallel e2e check.
