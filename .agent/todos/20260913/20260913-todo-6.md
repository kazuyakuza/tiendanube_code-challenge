# TODO 05 – Transactions Controller & Error Handling

## Goal

Expose the orchestration logic through a proper HTTP endpoint and define how the API behaves under failure scenarios.

Concrete deliverables:

1. `POST /v1/transactions` controller wired to `TransactionsService`.
2. API Key protection on the endpoint.
3. Full Swagger documentation for the operation.
4. Clear, structured error responses.
5. An explicit decision (and implementation) for the partial-failure case (transaction created, receivable failed).
6. Optional response-body toggle via environment configuration.

## Context

- TODO 01 provided versioning, Swagger skeleton, API Key guard and the global ValidationPipe.
- TODO 02 provided all request/response DTOs.
- TODO 04 provided `TransactionsService.create()`.

After this TODO the API should be usable end-to-end through HTTP (and through Swagger UI).

## Task 1. Controller

### 1.1 Endpoint

```http
POST /v1/transactions
Header: x-api-key: <API_KEY>
Content-Type: application/json
```

- Must be versioned under `/v1`.
- Must be protected by the API Key guard created in TODO 01.
- Request body: `CreateTransactionDto`.
- Success response: `201 Created`.

### 1.2 Response behaviour (configurable)

The default behaviour is to return the full created resources:

```json
{
  "transaction": { ... },
  "receivable":  { ... }
}
```

Defined environment variable (validated in the ConfigModule) can change this behaviour:

```env
TRANSACTIONS_RETURN_BODY=true   # default
```

- When `true` → respond with `201` + the body above.
- When `false` → respond with `201` and an empty body.

### 1.3 Swagger

Annotate the controller method with:

- `@ApiOperation`
- `@ApiBody` (linked to `CreateTransactionDto`)
- `@ApiCreatedResponse` (linked to `CreateTransactionResponseDto`)
- `@ApiUnauthorizedResponse`, `@ApiBadRequestResponse`, `@ApiServiceUnavailableResponse` (or equivalent)
- Security requirement for `x-api-key`

After this TODO a developer should be able to open `/docs`, authorize with the API key, and successfully execute the operation.

## Task 2. Error handling & consistency

### 2.1 Error categories the API must handle cleanly

| Situation                                         | Suggested HTTP status | Notes                                      |
|---------------------------------------------------|-----------------------|--------------------------------------------|
| Validation error (DTO)                            | 400                   | Already handled by the global ValidationPipe |
| Missing / invalid API Key                         | 401                   | API Key guard                              |
| Numerator unreachable or retries exhausted        | 503                   | Service unavailable                        |
| json-server unreachable or returns 5xx            | 503                   | Service unavailable                        |
| json-server returns 4xx (unexpected)              | 502 or 500            | Bad gateway / internal error               |
| Unexpected internal error                         | 500                   | Generic fallback                           |

Prefer NestJS built-in exceptions (`BadRequestException`, `UnauthorizedException`, `ServiceUnavailableException`, etc.) or define custom when/where required. Include details in the msg (uncompleted examples: `'Numerator unreachable'`, `Numerator retries exhausted`, etc).

### 2.2 Partial failure (transaction written, receivable failed)

- If `createReceivable` fails after `createTransaction` succeeded, attempt to delete the transaction that was just created (`DELETE /transactions/:id`).  
- Maybe handle the deletion in another class, so we can implement a retry loop with a sleep and max retries.
- If compensation also fails (despite the retries), log the inconsistency and still return an error to the client.  
- The goal is to reduce (not necessarily eliminate) orphans.

### 2.3 Global exception filter

If you do not already have one, consider a simple global filter that:

- Catches unknown errors and returns a consistent JSON shape, e.g.:

```json
{
  "statusCode": 500,
  "message": "Internal server error",
  "error": "Internal Server Error"
}
```

- Does not leak stack traces in production (`NODE_ENV === 'production'`).

## Task 3. Module & wiring

- Register `TransactionsController` inside `TransactionsModule`.
- Apply the API Key guard on the controller or on the specific route.
- Make sure `TransactionsModule` is imported by `AppModule`.

## Out of scope

- Unit / e2e tests (next TODO)
- Rate limiting, circuit breakers, advanced observability
- Changing the Numerator or json-server clients themselves

## Implementation guidance

- Keep the controller thin: validate → call service → return. No business logic in the controller.
- Prefer explicit HTTP status decorators (`@HttpCode(201)`) so the contract is obvious.
- After this TODO the following manual test should succeed:
