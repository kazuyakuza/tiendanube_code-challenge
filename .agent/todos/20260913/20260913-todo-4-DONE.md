# TODO 03 – External Clients (Numerator API + json-server)

## Goal

Implement the two outbound HTTP clients that the orchestration layer will later use:

1. **Numerator client** – responsible for generating unique sequential IDs using optimistic concurrency (`test-and-set`) with retries.
2. **json-server client** – responsible for persisting transactions and receivables.

By the end of this TODO both clients must be fully usable as injectable NestJS providers.  
No orchestration logic, no controller changes, and no fee calculation yet.

## Context

- TODO 01 provided the NestJS foundation, ConfigModule and the environment variables `NUMERATOR_API_URL` and `JSON_SERVER_URL`.
- TODO 02 defined the DTOs and the shape of the data that will eventually be sent to json-server.
- Both external services are set-up in the docker-compose root file. This services will be running when required (don't run docker cmds, ask user).

Use `@nestjs/axios` (`HttpService`) for all HTTP calls.  
Do not introduce any other HTTP library.

## Task 1. Numerator Client [DONE]

### 1.1 Responsibility

Provide a single high-level method that the rest of the application will call:

```ts
getNextId(): Promise<string>
```

- Returns a unique ID as a **string** (json-server expects string IDs).
- Internally uses the Numerator API’s atomic `test-and-set` endpoint.
- Handles concurrent callers safely through retries.

### 1.2 Numerator API contract

| Method | Path                       | Purpose                                      |
|--------|----------------------------|----------------------------------------------|
| GET    | `/numerator`               | Returns `{ numerator: number }`              |
| PUT    | `/numerator/test-and-set`  | Body: `{ oldValue, newValue }` – atomic CAS  |

On success the CAS endpoint returns `{ numerator: newValue }`.  
On conflict it returns HTTP 400 with a body that includes the current value.

Treat the CAS operation as **atomic** (as documented by the challenge).

### 1.3 Required behaviour of `getNextId()`

```text
loop up to MAX_RETRIES times:
  1. GET current numerator
  2. candidate = current + 1 // verify current is a valid number
  3. attempt test-and-set(oldValue = current, newValue = candidate)
  4. if success → return String(candidate)
  5. if conflict → wait a short backoff and retry
after MAX_RETRIES → throw a meaningful error (implement error class)
```

Config .env vars:

- `MAX_RETRIES`: default 10
- Backoff: default 20ms with a very light exponential backoff.

The method must never return an ID that another concurrent caller could also have obtained.

### 1.4 Error handling

- Network / timeout errors from the Numerator service should surface as a clear application exception (custom domain error class).
- Exhausted retries should also produce a clear error so the orchestration layer can abort before writing anything.
- Received invalid number also must produce a clear error.

### 1.5 Implementation notes

- Create a dedicated NestJS module + service (e.g. `NumeratorModule` / `NumeratorService`).
- Inject `HttpService` and `ConfigService`.
- Base URL must come from `NUMERATOR_API_URL` (use `ConfigService`).
- Keep the low-level HTTP calls (get current, test-and-set) as private methods if it improves readability.

## Task 2. json-server Client [DONE]

### 2.1 Responsibility

Expose two methods that mirror the resources defined by the challenge:

```ts
createTransaction(payload: CreateTransactionPayload): Promise<TransactionResponseDto>
createReceivable(payload: CreateReceivablePayload): Promise<ReceivableResponseDto>
```

Reuse the DTOs created in TODO 02.

### 2.2 json-server endpoints

| Method | Path            | Body (relevant fields)                                      |
|--------|-----------------|-------------------------------------------------------------|
| POST   | `/transactions` | `id`, `value`, `description`, `method`, `cardNumber` (last 4), `cardHolderName`, `cardExpirationDate`, `cardCvv` |
| POST   | `/receivables`  | `id`, `transaction_id`, `status`, `create_date`, `subtotal`, `discount`, `total` |

Both endpoints expect the `id` to be supplied by the caller.

### 2.3 Implementation notes

- Create a dedicated module + service (e.g. `JsonServerModule` / `JsonServerService`).
- Inject `HttpService` and `ConfigService`.
- Base URL must come from `JSON_SERVER_URL` (use `ConfigService`).
- On success, return the body that json-server responds with (it usually echoes the created resource).
- On failure (4xx/5xx), throw a clear exception so the orchestration layer can decide what to do.

### 2.4 Payload shapes (for clarity)

**Transaction payload** (what you will eventually send):

```ts
{
  id: string;                  // from Numerator
  value: string;
  description: string;
  method: 'debit_card' | 'credit_card';
  cardNumber: string;          // already masked (last 4)
  cardHolderName: string;
  cardExpirationDate: string;
  cardCvv: string;
}
```

**Receivable payload**:

```ts
{
  id: string;                  // from Numerator
  transaction_id: string;
  status: 'paid' | 'waiting_funds';
  create_date: string;         // ISO-8601 recommended
  subtotal: string;
  discount: string;            // "2" or "4"
  total: string;
}
```

The client itself does **not** calculate fees or mask card numbers; it only transports the data it receives.

## Task 3. Module registration [DONE]

Both clients should be proper NestJS modules that:

- Import `HttpModule` (from `@nestjs/axios`) – optionally configured with a timeout.
- Export their service so other modules can inject them.
- Can be imported later by the Transactions module.

Suggested structure:

```text
src/
├── numerator/
│   ├── numerator.module.ts
│   └── numerator.service.ts
├── json-server/
│   ├── json-server.module.ts
│   └── json-server.service.ts
└── ...
```

## Configuration & resilience

- All URLs come from the validated environment (never hard-coded and don't use process.env, use `ConfigService`).
- Consider setting a reasonable timeout on the Axios instance (e.g. 3–5 seconds) so a hanging external service does not block the request indefinitely.
- Logging: log the attempts made by `getNextId()` when a conflict occurs. Avoid logging sensitive card data.

## Out of scope for this TODO

- Orchestration logic (obtaining two IDs + creating both resources in sequence)
- Fee calculation
- Card-number masking
- Controller endpoints
- Retry policy for the json-server calls (simple fail-fast is enough for now)
- Unit / e2e tests (will come later)

## Implementation guidance

- Keep each client focused on a single external system.
- Prefer small, testable private methods inside `NumeratorService` for “get current” and “test-and-set”.
- Make the retry loop easy to read; a simple `for` + `await sleep()` is perfectly acceptable for this challenge.
- After this TODO a developer should be able to inject `NumeratorService` and `JsonServerService` into any other service and call them independently.
